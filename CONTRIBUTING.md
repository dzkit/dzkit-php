# Contributing to dzkit-php

Thanks for helping. Issues and pull requests are welcome in العربية, Français or English.

## Where a change belongs

- **A value or a rule** (an IRG bracket, the minimum wage, a wilaya name, a phone block): in [dzkit-spec](https://github.com/dzkit/dzkit-spec), with its official source. Every dzkit package takes its values from there, so the fix reaches every language.
- **How PHP does it** (a bug, a PHP-specific behaviour, the API, the docs): here.

## Setup

PHP 8.1 or later and Composer.

```bash
composer install
vendor/bin/phpunit
```

The tests include every shared test case of dzkit-spec (`tests/SpecTest.php`, reading `spec/vectors.json`), PHP-specific cases (`tests/PhpSpecificTest.php`) and the list of public classes and methods (`tests/ApiTest.php`).

## Rules of thumb

- **Every value comes from dzkit-spec.** `src/Generated/SpecData.php` is generated by `php bin/generate` from `spec/dzkit-spec.json`. Never edit it by hand: CI fails if it doesn't match.
- **Validators, parsers and formatters never throw**, whatever they receive. Calculations throw `DzkitException` with a code. See [OPERATIONS.md](https://github.com/dzkit/dzkit-spec/blob/main/OPERATIONS.md).
- **No floating point for money.** Amounts go through `Input::cents()`, and payroll works in whole centimes (tenths of a centime inside the IRG).
- **No runtime dependencies.** PHPUnit is a development dependency only.
- **Real examples beat theory.** A RIP from a real document or an IRG amount from a real payslip: anonymise them, then add them as test cases in dzkit-spec.

## Following a new dzkit-spec release

```bash
php bin/update-spec v0.5.0   # downloads into spec/ and checks the checksums
php bin/generate             # regenerates src/Generated/SpecData.php
vendor/bin/phpunit
```

Review the diff of `src/Generated/SpecData.php`: it shows exactly which values changed. If a test fails, the spec added or changed something: adapt `src/` or the runner in `tests/SpecTest.php`, note it in `CHANGELOG.md`, and open a pull request.

## Releasing

Composer reads versions from Git tags; Packagist picks up each new tag on its own through its GitHub hook. Nothing is uploaded and no token is needed.

1. In a pull request, add a `## X.Y.Z — date` section to `CHANGELOG.md`, saying which dzkit-spec version it follows. Choose the number with the rule shared by every dzkit package: a fix that makes a wrong result right is a patch; anything that changes a correct result, removes something, or turns a result into an error (or the reverse) is a minor version before 1.0 (see [dzkit-spec's GOVERNANCE.md](https://github.com/dzkit/dzkit-spec/blob/main/GOVERNANCE.md)).
2. Merge it once CI is green.
3. On GitHub, go to **Releases → Draft a new release**, create the tag `vX.Y.Z` on `main`, paste the changelog notes, and click **Publish release**. Packagist shows the new version within a minute.

A published version never changes: a mistake is fixed by a new patch release, never by moving or deleting a tag.
